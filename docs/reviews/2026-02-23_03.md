# コードレビュー: iOS App Recorder (第3回)

レビュー日: 2026-02-23
レビュアー: iOS 音声/動画エンジニア視点

## 全体評価

2回のレビューを経て基本的なバグは潰されている。アーキテクチャは整っており、ゼロコピー IOSurface キャプチャ、ロックフリー SPSC リングバッファ、プライミング補償付き AAC エンコード、drawable ライフサイクル管理など、リアルタイム A/V パイプラインの要所を的確に押さえている。以下は残存する指摘事項。

---

## High

### 1. ~~VideoToolbox DataRateLimits がビットレート上限と同値~~ ✅ 修正済み

- **ファイル:** `VideoEncoder.m:116`
- **問題:** `kVTCompressionPropertyKey_DataRateLimits`（ハードキャップ）を平均ビットレートと同値に設定。I フレームは P フレームの数倍のサイズになるため、キーフレーム発行時にビットが足りずエンコーダが品質を大幅に落とす。2560x1440 HEVC @120fps では特に顕著。
- **修正内容:** ハードキャップを平均の 1.5 倍に変更。

### 2. ~~PULL コマンドでセキュリティチェック後のパスが不一致 (TOCTOU)~~ ✅ 修正済み

- **ファイル:** `ControlServer.m:252-265`
- **問題:** `stringByStandardizingPath` は `..` は解決するがシンボリックリンクは解決しない。チェックには `resolvedPath` を使いつつ、ファイル操作には元の `path` を使っていたため、tmp 配下にシンボリックリンクが存在する場合に tmp 外のファイルを読み出せる可能性があった。
- **修正内容:** `realpath(3)` でシンボリックリンクも完全解決。`NSTemporaryDirectory()` 側も `realpath` で正規化（iOS の `/var` → `/private/var` シンボリックリンク対応）。以降すべて `resolvedPath` を使用。

### 3. ~~nextDrawable フックのキャプチャタイミングと PTS の乖離~~ ✅ 修正済み (コメント追記)

- **ファイル:** `FrameCapture.m:125-130`
- **問題:** `nextDrawable` の時点で PTS を `mach_absolute_time()` から計算しているが、実際の GPU レンダリングはこの後に発生。IOSurface の暗黙的同期により VT ハードウェアエンコーダは GPU 完了後のフレームを読むが、PTS はレンダリング前の時刻。120fps で 1-2 フレーム分（8-16ms）の系統的な A/V オフセットが発生し得る。
- **修正内容:** 制限事項と改善案（`addPresentedHandler:` の導入）を TODO コメントとして明記。

## Medium

### 4. ~~FrameCapture: `_captureSize` の直接 ivar アクセスが atomic を迂回~~ ✅ 修正済み

- **ファイル:** `FrameCapture.m:56`
- **問題:** `captureSize` は `atomic` プロパティだが、`_captureSize` の直読みは atomic getter を経由しない。`RecorderCore.startRecording` が別スレッドから読むため、`CGSize`（16 バイト struct）の部分読み取り（tearing）が ARM64 で理論上発生し得る。
- **修正内容:** `self.captureSize` で読むように変更。

### 5. ~~FrameCapture: recordingStartTime と capturing の間にメモリバリアがない~~ ✅ 修正済み

- **ファイル:** `FrameCapture.m:43-46`, `FrameCapture.h:23`
- **問題:** `capturing`、`startTimeSet`、`recordingStartTime` がすべて nonatomic。Metal レンダリングスレッドが `capturing = YES` を先に観測し `recordingStartTime` の書き込みを見逃すと、最初の数フレームの PTS が 0 になる。`AudioCapture` 側では `stdatomic` の `release/acquire` を正しく使っているが、`FrameCapture` 側はこのパターンが欠けていた。
- **修正内容:** `AudioCapture` と同様に `sFrameCapturing` / `sFrameRecStartTimeSet` / `sFrameRecStartTime` を static 変数として導入し、`atomic_store_explicit(release)` / `atomic_load_explicit(acquire)` で順序を保証。

### 6. ~~PULL コマンドのソケットに送信タイムアウトがない~~ ✅ 修正済み

- **ファイル:** `ControlServer.m:296-316`
- **問題:** クライアントが読み取りを停止した場合、`write()` が無期限にブロック。ブロックされたスレッドが蓄積する可能性。
- **修正内容:** `SO_SNDTIMEO` を 60 秒に設定。

### 7. ~~MP4Muxer: isReadyForMoreMediaData == NO 時のサンプル無声ドロップ~~ ✅ 修正済み

- **ファイル:** `MP4Muxer.m:139-143, 166-170`
- **問題:** AVAssetWriterInput がバックプレッシャーをかけた場合、フレームが無言でドロップ。長時間録画でディスク I/O が間に合わない場合に映像のジャンプとして顕在化する。
- **修正内容:** `videoDropCount` / `audioDropCount` カウンタを追加し、`finishWithCompletion:` 時にログ出力。

### 8. ~~stop 完了チェーンがメインキューを経由~~ ✅ 修正済み

- **ファイル:** `VideoEncoder.m:228`, `AudioEncoder.m:475`, `MP4Muxer.m:182-213`
- **問題:** stop の各段階の completion がメインキューに dispatch されるため、チェーン全体（video stop → audio stop → mux finish）が 3 回メインキューを経由。ControlServer の STOP コマンドがセマフォでブロック待ちしている場合、メインキュー dispatch はデッドロックの可能性がある。
- **修正内容:** 内部チェーンでは completion を直接呼び出し、メインキュー経由を排除。

## Low

### 9. ~~VideoEncoder: static カウンタがプロセス全体で共有~~ ✅ 修正済み

- **ファイル:** `VideoEncoder.m:24-27`
- **問題:** `sEncodeCount` / `sOutputCount` が static でプロセス全体共有。`start` でリセットされるため現状は問題ないが、意図が不明確。
- **修正内容:** `@public` 付きインスタンス変数 `_encodeCount` / `_outputCount` に移動。VT 出力コールバック（C 関数）からアクセスするため `@public` が必要。

### 10. ~~ControlServer: 同時接続数に制限がない~~ ✅ 修正済み

- **ファイル:** `ControlServer.m:90`
- **問題:** 各クライアントが `dispatch_async` で global queue に dispatch される。悪意あるクライアントが大量接続するとスレッドが枯渇する。
- **修正内容:** `dispatch_semaphore` で同時接続数を 4 に制限。

### 11. ~~AudioEncoder: aacOutputBufferSize の余裕が少ない~~ ✅ 修正済み

- **ファイル:** `AudioEncoder.m:113`
- **問題:** `1024 * channels * 2` = ステレオで 4096 bytes。AAC-LC の最大フレームサイズ（約 1536 bytes）に対して余裕が少ない。
- **修正内容:** 8192 固定に変更。

### 12. ~~RecorderCore: `isRecording` が nonatomic~~ ✅ 修正済み

- **ファイル:** `RecorderCore.h:8`, `RecorderCore.m:8`
- **問題:** ControlServer スレッド、FrameCapture デリゲート、AudioCapture デリゲートなど複数スレッドから参照される BOOL プロパティが nonatomic。
- **修正内容:** `atomic` に変更。
